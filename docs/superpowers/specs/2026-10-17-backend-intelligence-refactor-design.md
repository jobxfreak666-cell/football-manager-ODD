三份导出已按每个文件的补丁内容核对，代码一致；只应用一次 `FMODD-改动导出/改动_含新增文件.patch`，共 36 个文件，包含新增钱包 +100 测试。首批服务提取时，已导入文件中仅 `src/fm_odds_web.py` 因提取而再次变化，其余当时与导入快照一致；此后钱包 +100B 的后续改动又涉及部分代码、翻译与测试文件，故不再以固定数量描述当前差异。

必须保留用户先前要求的四项行为：钱包作弊允许 100/500/5000 且不动银行；心理辅导固定“彻底释怀”、每次钱包支付换算后的 100K 并保留失败退款；移除免费购买开关/API/购买分支；比赛情报指定价格为 40M/60M/80M，随机价格为 20M/30M/60M，经既有换算且先银行后钱包，`pricing_basis` 为 `fixed_price`。

保留 FM24/FM26 共用行为、金额缩写和多语言支持。用户提供的 v2 预览作为视觉参考；已使用接入后的真实前端和隔离示例数据生成 7 张预览，辅导金额实际显示 `£100.0K` / `£300.0K`。本次服务提取不额外改变产品 UI；之后的钱包 +100B 入口调整属于用户追加要求，见下文。

执行方式按用户偏好调整为 DeepSeek 优先实现，Codex 检查 diff、运行测试并整合；实现后独立审查未发现提取引入的实质问题。DeepSeek 的终端权限初始化不可用，实际代码由其文件工具完成，验证由 Codex 执行。

## 目标与范围

用户希望重构后端结构，提高可维护性。首批从 `src/fm_odds_web.py` 抽取完整的比赛情报用例，建立可单独理解、测试的应用模块，并保留既有调用接口与行为。后续领域可沿同样方式逐块迁移；本批不宣称完成全库重构。

成功标准：情报用例不再直接实现在 2.34 万行的 HTTP/运行时入口中；新模块具有明确依赖和测试；可运行的情报边界与相关定向回归通过；缺少原生依赖时明确记录 HTTP/原生集成未验证。

## 方案比较

1. **推荐：按领域提取比赛情报应用服务。** 探测、展示、购买形成完整生命周期；现有情报测试可作为迁移基线。需要仔细保留锁、账户作用域及模块级替换点。
2. 提取 HTTP 路由注册。边界较简单，但主要收益是移动声明，仍未减少 `LocalOddsState` 的业务职责。
3. 首先拆分刷新主循环。涉及连接、结算、后台线程和存档切换，回归范围明显更大，适合作为后续独立批次。

## 应用边界

以下方法保持参数、返回值和异常语义：

- `_probe_match_intelligence_if_idle(*, force=False) -> bool`
- `watch_match_intelligence() -> None`
- `public_match_intelligence() -> dict`
- `buy_match_intelligence(payload) -> dict`

服务不导入 HTTP 入口，不复制一份运行时状态，不拥有 FM 原生布局或账户持久化格式。运行时适配层显式提供状态访问、已有保护操作及所需函数；不传入整个模块、使用动态属性代理或引入通用服务框架。原 `fm_odds_web` 函数替换点继续在调用时解析，避免破坏既有测试和调用方。

后台监控的循环与调度继续由运行时负责，服务处理单次探测；外部 `watch_match_intelligence` 入口保持可用。

## 必须保持的行为

- 探测检查已验证存档、刷新、协调、切档及节流门禁；仅非阻塞尝试内存锁。
- 探测快照、候选合并、错误记录和 `data_version` 更新保留现有顺序，不增加游戏读取或探测次数。
- 购买先在内存锁内读取游戏时间，释放后进入状态锁；绑定账户、扣费、公共投影和缓存发布仍在原保护范围。
- 候选必须仍在已发布市场且未超过获取窗口；游戏时间未知时拒绝购买。
- 随机购买沿用 `client_submission_id` 幂等语义，重复请求复用既有购买，不重新随机或重复扣费。
- 缓存作用域、独立副本、已购买结果保密、金额、错误文案及响应字段保持不变。
- 不改变 API、前端、账户或存档格式、赔率模型、FM 版本支持和原生写入规则。
- 如发现既有并发缺陷，单独记录并评估，不混入行为保持重构。
